Configuration — system inputs

The first screen of the setup wizard. These are the chain's own inputs; everything device-specific lives on the cells page.

All of these can be changed later without reinstalling: Settings → Devices & services → Energy Balancer → Configure. The same screen is used for setup and for reconfiguration.

Required sensors

Without these three the chain cannot run, and the integration will refuse to start with a message naming the missing one. There is no sensible default for any of them.

FieldKeyExpects
Solar production solar_sensor An entity reporting current PV production in watts. Positive.
House consumption house_sensor An entity reporting current household load in watts. Positive.
Grid power grid_sensor An entity reporting grid exchange in watts, positive when importing.

House consumption should exclude the devices you are steering. If your house sensor already contains the car charger, the chain sees that load twice: once as consumption and once as a cell. Either point at a sensor that excludes them, or list the offending entities under House includes below and they will be subtracted for you.

Optional inputs

FieldKeyDefaultWhat it does
House includes house_includes empty Entities whose power is already counted inside the house sensor and must be subtracted from it. Use when you cannot get a clean house figure.
Solar forecast remaining today forecast_sensor — Expected remaining PV yield today, in kWh. This is the one forecast input the algorithm actually steers on: it is what lets a battery hold back in the morning because the afternoon will fill it anyway.
External pool charge % charge_pct_sensor — Defers the charge decision to an external policy. See Concepts for the contract; the sensor needs a mode attribute as well as a numeric state.
Peak import limit fallback peak_limit_w 3500 W
range 0–30000		 The import ceiling used when no limit sensor is configured or all of them are unavailable.
Peak limit sensors peak_limit_sensors empty One or more entities carrying an import limit in watts. The highest value across them is used. A common pair is a manual ceiling plus your running monthly-peak sensor.
Your peak maximum peak_max_w 0 (not set)
range 0–30000		 A ceiling you allow on top of the others, for a month in which you know you will need more (a winter month with a car to charge). It can only raise the ceiling: its lower bound follows the higher of the monthly peak and peak_limit_w, because a peak that is already spent cannot be won back.
15-minute block demand block_demand_sensor — The running 15-minute average grid import, the figure a capacity tariff bills. With it, the battery tier gets a budget for the rest of the current quarter hour instead of reacting to the momentary grid value. Without it, there is no block budget.
Monthly peak sensor month_peak_sensor — Which of the peak_limit_sensors carries the monthly peak. Meters tend to keep showing last month's peak for a while after midnight on the 1st; naming the sensor here lets the month-rollover windows below treat that stale value. Leave empty to switch the rollover handling off.
Month-start peak policy month_start_peak_policy previous What the monthly-peak reading counts as inside a rollover window: previous takes it as-is, configured caps it at peak_limit_w, zero ignores it.
Month-start window month_start_window_min 30 min
range 0–240		 How long after midnight on the 1st the policy applies. 0 = off.
Month-end window month_end_window_min 0 (off)
range 0–1440		 The same cap, applied before midnight on the last day of the month. A battery that is still charging hard at 23:59 is still charging at 00:01, and that quarter hour sets the new month's peak, so the brake has to be on before the boundary.
Update interval update_interval_seconds 10 s
range 5–300		 How often the chain runs. Ten seconds keeps up with a car charger ramping. Raising it reduces database churn at the cost of reaction time.
Observer mode observer_mode on Compute and publish, never actuate. Leave it on until the numbers look right.
Import price import_price_per_kwh 0
range 0–5		 €/kWh for imported energy. A fixed number, or an entity id if your price varies. Applied incrementally: each tick's kWh delta is priced at the rate valid at that moment, so a changing tariff is handled correctly.
Export price export_price_per_kwh 0
range 0–5		 €/kWh for exported energy. Same rules as the import price.

The import ceiling, in one rule. ceiling = max(peak_limit_w, monthly peak, peak_max_w). peak_limit_w is what you want the month to cost and is the whole ceiling at the start of a month. The monthly peak is what already happened: once the month stands at that value, staying below it saves nothing. peak_max_w is the extra room you choose to allow.

Fixed value or live entity

Several settings accept either a number or an entity id. Give a number and the integration owns it — it will also create a slider for it so you can drag it on a dashboard. Give an entity id and that entity becomes the single source of truth: the integration reads it live every tick and creates no slider, because two knobs for one value is how values start disagreeing.

Recognised entity prefixes are sensor., input_number., input_select., number. and binary_sensor..

What happens to a bad value

Every parameter passes through one validation layer when the integration starts. Nothing crashes and nothing is silently skewed:

  • A value outside its range is clamped to the nearest bound.
  • A value of the wrong type falls back to the documented default.
  • Either way one warning is logged, naming the parameter, the bad value and the default that replaced it.
  • A missing required sensor is the exception: that raises, with a message telling you which one.

So if a setting is not doing what you expect, the log is the first place to look — the answer is usually already written there.
